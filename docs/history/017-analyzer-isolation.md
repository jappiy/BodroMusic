# 017 — Анализатор: ffmpeg, дочерний процесс, лимит попыток

- **Дата:** 2026-10-20
- **Версии:** bodrod 0.14.0, воркер анализа 0.2.0
- **Релиз с APK:** не требуется — только сервер и анализатор (новое поле `skipped` в `/api/v1/analysis` приложение
  игнорирует)
- **Образы:** `ghcr.io/jappiy/bodromusic-server:0016967`, `ghcr.io/jappiy/bodromusic-analyzer:0016967`
- **Статус:** реализовано; pytest (анализатор 8 + 3 теста ffmpeg, которые идут в CI; bodrod 159); на сервере не проверено

## Задание

1. Не загружать аудио через `MonoLoader`: декодировать системным ffmpeg в подпроцессе
   (`ffmpeg -i file -f f32le -ac 1 -ar 16000 -t 120 -`) и передавать в Essentia numpy-массив. Закрывает opus, m4a
   («Could not find stream information» на Zivert) и любые форматы. В образ — `ffmpeg` из apt.
2. Анализ каждого трека — в дочернем процессе: нативный краш убивает только воркер, трек помечается `failed` и
   отправляется в bodrod с ошибкой.
3. Треки, упавшие 2–3 раза, помечать в bodrod «не анализировать», чтобы они не возвращались в `/analysis/next`.

## Что выяснено

- Essentia-загрузчики (`MonoLoader`, `AudioLoader`) на части файлов падали нативно — Python-`try` из 016 такое не
  ловит, контейнер перезапускался и после истечения аренды (30 мин) получал тот же трек снова.
- В 016 упавший трек больше не выдавался вовсе — с ffmpeg у таких треков (opus, m4a) появился шанс, поэтому вместо
  «никогда» сделан счётчик попыток.

## Что сделано

- `analyzer/bodro_analyzer/decode.py`: `ffprobe` (длительность, каналы) + `ffmpeg … -f f32le -ac 2 -ar 44100 -t 120`
  в подпроцессе с таймаутом; ошибка → `DecodeError` с последней строкой stderr. Одно декодирование на трек: стерео
  44.1 кГц для громкости, моно для темпа и тональности, 16 кГц для эмбеддинга — `es.Resample`. Треки длиннее 150 с
  анализируются с 30-й секунды (вступление нехарактерно). `duration` в признаках — длительность всего файла (ffprobe).
  Громкость EBU R128 — только для исходного стерео, как раньше.
- `analyzer/bodro_analyzer/extract.py`: загрузчики Essentia не используются.
- `analyzer/bodro_analyzer/isolated.py`: `IsolatedExtractor` — дочерний процесс (`spawn`) грузит модели один раз
  (а не на каждый трек, как было бы с `maxtasksperchild=1`) и анализирует по пути из `Pipe`. Ожидание —
  `connection.wait([pipe, sentinel])`: смерть процесса (сигнал, `os._exit`, OOM) или зависание дольше
  `TRACK_TIMEOUT_S` (600 с; процесс убивается) → `AnalysisCrashed`, воркер шлёт `failed` («Процесс анализа упал
  (анализ): сигнал SIGSEGV»), следующий трек получает новый процесс. Перезапуск каждые 200 треков (утечки нативных
  библиотек). Модели не загрузились → `ExtractorUnavailable`: это не ошибка трека, воркер останавливается, Docker
  перезапускает контейнер.
- `analyzer/Dockerfile`: `ffmpeg` из apt. CI анализатора ставит ffmpeg и numpy.
- bodrod (`server/bodrod/reco/analysis.py`): `audio_features.attempts` — неудач подряд. Упавший трек выдаётся снова
  не раньше чем через час (`RETRY_DELAY_MS`); после `MAX_ATTEMPTS = 3` не выдаётся. Успех обнуляет счётчик. Аренда,
  истёкшая без результата (воркер пропал вместе с треком), — тоже неудача («Нет результата за 30 минут…»).
  Миграция: старые ошибки — `attempts = 1` (ещё две попытки). `GET /api/v1/analysis` — новое поле `skipped`
  (исключённые; входят и в `errors`).
- Тесты: `analyzer/tests/test_isolated.py` (краш, зависание, ошибка Python, перезапуск по `max_tasks`, незагружаемые
  модели), `test_decode.py` (opus моно, ограничение 120 с, битый файл; без ffmpeg пропускаются),
  `server/tests/test_analysis.py` (повтор через час, три неудачи, истёкшая аренда, обнуление, миграция).

## Что нужно сделать на сервере

В проекте DSM — теги образов, остальное без изменений:
```yaml
  bodrod:
    image: ghcr.io/jappiy/bodromusic-server:0016967
  analyzer:
    image: ghcr.io/jappiy/bodromusic-analyzer:0016967
```
Pull + up. Чтобы проанализировать заново и исключённые треки — `UPDATE audio_features SET attempts = 0 WHERE error
IS NOT NULL` (или удалить строки с ошибкой).
