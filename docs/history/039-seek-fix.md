# 039 — Иногда трек нельзя перемотать

- **Дата:** 2026-10-26
- **Версии:** приложение 0.30.0 (`versionCode 31`)
- **Релиз с APK:** https://github.com/jappiy/BodroMusic/releases/tag/v0.30.0
- **Статус:** реализовано; сборка и unit-тесты; воспроизведено рассуждением по коду Media3, на телефоне не проверено

## Задание

Пул задач 2026-10-26, п. 5 (приоритет): трек играет, но перемотка не работает (как будто не скачан); помогает только
переключение. Проверить гипотезы (транскодинг без Content-Length/Range — `estimateContentLength`, `format=raw`;
частичный кэш; кэширующий DataSource), логировать (URL без токенов, формат, транскодинг, кэш/сеть, ответ на seek),
fallback — переоткрыть поток с позиции или дождаться загрузки.

## Что выяснено — причина

- Транскодинг не виноват: «Оригинал» идёт с `format=raw`, транскодированный поток — с `estimateContentLength=true`
  (`SubsonicClient.streamUrl`, с 0.1x).
- **Причина — предзагрузка.** `StreamPrefetcher` кладёт в кэш начало двух следующих треков
  (`StreamDataSourceFactory.prefetch`, 1,5 МБ) запросом с границей (`setLength(bytes)`). `CacheDataSource` записывает
  длину файла в метаданные кэша только при запросе **без** границы — после предзагрузки длина трека в кэше
  неизвестна. Когда плеер доходит до этого трека, `CacheDataSource.open` отдаёт `C.LENGTH_UNSET` (начало читается
  из кэша), и экстрактор строит карту перемотки без длины: FLAC без SEEKTABLE, Ogg/Opus и MP3 без заголовка Xing
  перематываются только по длине файла → «неперематываемый» поток. Дальше плеер докачивает остаток запросом без
  границы, длина в кэше появляется — поэтому повторное открытие (переключение туда и обратно) «лечит».
- Второе звено: у неперематываемого трека Media3 убирает команду `COMMAND_SEEK_IN_CURRENT_MEDIA_ITEM`, и
  `MediaController.seekTo` из приложения молча игнорируется — пользователь не видит ни перемотки, ни ошибки.

## Что сделано

- `StreamDataSourceFactory.prefetch` → запрос без границы через `CacheWriter`, остановка, как только набрано 1,5 МБ
  и длина известна (`cacheAhead`). `ensureContentLength(songId, full)` — докачать «дыру» после закэшированного начала
  до ответа с длиной (или весь трек).
- `SeekRescue` (новый, в сервисе) и команда сессии `ru.bodro.music.SEEK`: приложение (`PlayerConnection.seekTo`)
  шлёт её, если текущий трек неперематываемый. Сервис узнаёт длину, переоткрывает поток (`replaceMediaItem` с URI
  `…?reopen=N` — тот же id и ключ кэша) и перематывает; не помогло — докачивает трек в кэш целиком и переоткрывает
  ещё раз; не помогло и это — сообщение «Перемотка в этом потоке недоступна…». `PlaybackCoordinator` не считает
  переоткрытие сменой трека (скроббл и история продолжаются).
- Журнал `Stream` (новый тип `PlayerEvent.Stream`): каждое открытие потока — id, с какой позиции (перемотка),
  оригинал / транскодирование, «кэш N КБ, затем сеть» или «сеть», известна ли длина; в деталях — путь и параметры
  `stream.view` без `u/t/s/p`. Шаги `SeekRescue` — туда же.

## Что осталось / проверить

- На телефоне: дать отыграть трек, чтобы следующий предзагрузился, переключиться и перемотать; журнал «Stream».
- Старые записи кэша (предзагруженные до 0.30.0) без длины лечатся `SeekRescue` при первой перемотке.
