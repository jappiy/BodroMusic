# 019 — Сводка обслуживания библиотеки, обложки в папках Lidarr

- **Дата:** 2026-10-23
- **Версии:** приложение 0.21.0 (`versionCode 22`), bodrod 0.16.0
- **Релиз с APK:** https://github.com/jappiy/BodroMusic/releases/tag/v0.21.0
- **Образ bodrod:** `bodrod:local`, собирается на NAS из папки (`docs/DEPLOY.md`); база не менялась (`requirements.txt` тот же)
- **Статус:** реализовано; pytest (173) и unit-тесты клиента зелёные локально; на сервере и телефоне не проверено

## Задание

Отчёт обслуживания библиотеки — переделать:
1. Вместо списка по трекам — сводка с цифрами: исправлено (по типам), в карантине, не исправлено (по причинам).
2. Детальный список оставить только для карантина (с кнопкой «вернуть»). Остальные категории — только счётчики.
3. Убрать чипсы-фильтры по категориям.
4. Папки Lidarr (`library/`): разрешить только добавление `cover.jpg`, если обложки нет (источник — Cover Art
   Archive по MBID из тегов/Lidarr). Теги и файлы там не менять.
5. Пропуски по правилу «папка Lidarr» не показывать в «Требует внимания» и не считать проблемой.

## Что выяснено

- «Требует внимания» раньше считался только по новым находкам: неисправимое пишется в отчёт раз в 30 дней
  (`maintenance_checked`), поэтому на следующую ночь счётчик падал до нуля, хотя проблемы оставались. Для сводки
  этого мало — у отметки «проверено» теперь хранится причина, и известные проблемы считаются каждый запуск.
- Пропуски в папках Lidarr («Папка Lidarr — не трогаем») составляли заметную часть «требует внимания»: короткие,
  теги, обложки.

## Что сделано

- Сервер (`server/bodrod/maintenance.py`):
  - причины не исправленного `REASONS` (`short_version`, `tags_unreadable`, `tags_not_found`, `cover_not_found`,
    `lidarr_cover_not_found`, `mismatch`) → счётчики `open_<причина>` в статистике запуска; `attention` = их сумма;
    `_known` считает уже известные проблемы, не дублируя их в отчёте; причина хранится в `maintenance_checked.reason`;
  - папки Lidarr: короткие, теги и вшивание обложек пропускаются молча (ни действия, ни счётчика);
    `_fix_lidarr_cover` кладёт `cover.jpg` из Cover Art Archive (`/release/<mbid>/front-1200`, затем
    `/release-group/…`). MBID — `_album_mbids`: теги файла (`read_album_mbids`), `mbz_album_id` из базы Navidrome,
    затем Lidarr (`/trackfile` исполнителя → альбом папки → отслеживаемый релиз и группа релизов);
  - `summary()` и `GET /api/v1/maintenance/summary` (`MaintenanceSummary`: `run`, `fixed`, `unresolved`,
    `quarantine`); для запусков до 0.16.0 причины берутся из действий по видам без пропусков Lidarr.
- Сервер, прочее: `db.py` (колонка `reason`, `active_quarantine`, `open_findings`, фильтр `attention` без пропусков
  Lidarr), `navidrome_db.py` (`NdSong.album_mbid`), `clients/lidarr.py` (`album`), `models.py`, `main.py`, `README.md`.
- Приложение: `ui/screens/settings/MaintenanceScreen.kt` переписан — карточка запуска, блоки «Исправлено»
  («Будет исправлено» в пробном режиме) и «Не исправлено» с цифрами, список карантина с «Вернуть»; чипсы и
  список действий удалены. `core:downloads` — `MaintenanceSummary`, `QuarantineItem`, `MaintenanceCount`,
  `DownloadsClient.maintenanceSummary()` (старые `maintenanceActions`/`MaintenanceAction` убраны из клиента).
- Тесты: `test_maintenance.py` — пропуски Lidarr не в отчёте и не в сводке; обложка Lidarr из Cover Art Archive по
  MBID из Lidarr, файлы не тронуты, «нет в CAA» остаётся в сводке при повторных запусках; сводка через API и возврат
  из карантина. `DownloadsClientTest` — разбор сводки.

## Что нужно сделать на сервере

Обновить bodrod до 0.16.0 по [`docs/DEPLOY.md`](../DEPLOY.md), «Как обновить (только код)»: `robocopy` папки
`server` на NAS (анализатор не менялся) → Container Manager, проект `bodrod`: «Остановить» → «Создать». База и
переменные не менялись. Обложки в папках Lidarr появятся после ночного запуска или «Запустить сейчас».
