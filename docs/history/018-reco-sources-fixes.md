# 018 — Рекомендации: привязка архива Яндекса, ошибки источников, статусы кандидатов, счётчик анализа

- **Дата:** 2026-10-23
- **Версии:** приложение 0.20.0 (`versionCode 21`), bodrod 0.15.0
- **Релиз с APK:** https://github.com/jappiy/BodroMusic/releases/tag/v0.20.0
- **Образ bodrod:** `ghcr.io/jappiy/bodromusic-server:<хеш>` — см. «Что нужно сделать на сервере»
- **Статус:** реализовано; pytest (171) и сборка APK. На реальном сервере не проверено.

## Задание

Исправления экрана «Рекомендации» и статистики источников (bodrod и клиент):

1. **Привязка архива Яндекса к пользователю.** Источник «Архив Яндекса» пишет «Архив Яндекса этого пользователя
   пуст», хотя архив собран (аккаунты jappi и kalainidi: лайки, похожие, связи, резерв). Архив хранится под логином
   Яндекса, а источник ищет его по логину пользователя приложения. Нужно явное сопоставление
   «пользователь приложения → аккаунт Яндекса» (`YANDEX_USERS=логин_navidrome:логин_яндекса,...` и/или поле в
   приложении); источник и сбор архива используют его; без сопоставления — «Не привязан аккаунт Яндекса».
2. **ListenBrainz.** Добавить `LISTENBRAINZ_TOKEN` и `LISTENBRAINZ_USERS` (`логин_navidrome:логин_lb,...`) в шаблон
   секретов и compose с комментарием по формату. Значения владелец заполнит сам.
3. **Переключатели при ошибке конфигурации.** Источник с ошибкой — серый неактивный переключатель с текстом
   ошибки; в подборе не участвует.
4. **Счётчик «Анализ звучания».** «Проанализировано 9336 из 8410». Считать только треки библиотеки; привязать анализ
   к стабильному ключу (MBID, иначе хэш аудиоданных); периодически удалять записи отсутствующих треков (кроме
   карантина); миграция существующих данных.
5. **Разбивка статусов по источникам.** в очереди · качается · скачано · не найдено · в библиотеку · отклонено;
   загрузчик и время последней попытки у каждого кандидата; зависшие — обратно в очередь с лимитом попыток; счётчики в
   API; строка в приложении; резерв архива Яндекса — по той же схеме.

## Решения

- Привязка задаётся двумя способами: переменной `YANDEX_USERS` и в приложении (экран «Рекомендации» → «Архив Яндекса» →
  «Привязать» у аккаунта, только админы). Значение из приложения важнее переменной. Отдельное поле в настройках
  учётки делать не стали: экран рекомендаций видят только админы, а привязка общая для сервера.
- Совместимость: если файл токена назван именем пользователя Navidrome (схема 0.13.0), привязка не нужна.

## Что выяснено

- Анализ звучания хранился **по пути файла** (не по id Navidrome), а счётчик считал все строки `audio_features`. Поэтому
  в «проанализировано» попадали треки резерва (Navidrome их не видит), старые пути после перетегирования beets и
  регламента, файлы из карантина и удалённые треки. «Из N» — число треков в БД Navidrome.
- Харвестер записывал резерв и дизлайки под логином Яндекса. Если логин не совпадал с пользователем Navidrome,
  пул брал резерв у несуществующего пользователя, а сам логин попадал в список пользователей пула.
- Статистика источников шла только по `pool_owners.status`: «в очереди», «качается» и «не найдено» не различались.
  Резерв архива Яндекса (статус `candidate`) в разбивке не участвовал.

## Что сделано

Сервер (bodrod 0.15.0):
- `reco/yandex_links.py` — `YandexLinks`: пользователь Navidrome ↔ логин Яндекса (`YANDEX_USERS`, поверх него —
  привязки из приложения в `kv` `yandex.links`; без привязки — файл токена с именем пользователя). `YandexTokens`
  получает `link`: токен пользователя ищется через привязку. Харвестер работает по логинам Яндекса, резерв и чёрный
  список из дизлайков пишет привязанному пользователю (`owner`). Без привязки архив собирается, а предзакачка
  ждёт («Ждёт привязки к пользователю приложения»). `RecoStore.move_user_data` переносит записи, сделанные под логином
  Яндекса, при старте и при смене привязки. `PUT /api/v1/reco/harvest/links`. В статусе архива — `navidromeUser`,
  `reserveStates`.
- `YandexArchiveAdapter` работает через привязку. Ошибки: «Не привязан аккаунт Яндекса …» и «Архив Яндекса аккаунта X
  пуст: сбор ещё не прошёл». Ошибки источников (`describe(viewer)`) показываются для того, кто смотрит. ListenBrainz
  пишет, для какого пользователя нет LB. Источник с ошибкой в подборе не участвует (так было и раньше; теперь это видно).
- Статусы кандидатов: `store.candidate_state` (по статусу владельца и месту трека) → `queued`, `downloading`,
  `downloaded`, `notFound`, `promoted`, `rejected`. `source_stats` и `GET /api/v1/reco/engine` отдают их по каждому
  источнику. Для разбора отдельных треков — `GET /api/v1/reco/engine/candidates?source=…&state=…`.
- `pool_tracks`: новые колонки `loader`, `attempt_at`, `attempts`, `progress_sig`, `progress_at` (миграция `ALTER`).
  `PoolService._track_progress` записывает загрузчик (текущий источник цепочки или последний из попыток) и время
  попытки. `_stalled`: заявка без продвижения дольше `POOL_STALL_HOURS` (6) и не ждущая плановой паузы источника
  (`next_check_at`) отменяется через `worker.cancel` и ставится заново. После `POOL_MAX_ATTEMPTS` (3) трек получает
  статус `failed` («не найдено»). Предзакачка в резерв, висящая дольше часа (перезапуск посреди загрузки), снимается
  и пробуется снова, после трёх попыток — «не найдено».
- Анализ звучания (`reco/analysis.py`, `reco/audio_key.py`): у записи появились `mbid` (MBID записи из
  `media_file.mbz_recording_id`), `audio_hash` (хэш аудиоданных без тегов: MD5 из STREAMINFO FLAC; MP3 без
  ID3v2/ID3v1/APE; `mdat` MP4; звуковые страницы Ogg; первый мегабайт + размер) и `keyed`.
  - Новый путь без анализа получает готовый результат, если тот же звук уже проанализирован (`_adopt`).
  - Раз в час `maintain()`: вычисляет ключи старых записей (по файлу, копии в карантине или MBID пропавшего трека в БД
    Navidrome), переносит анализ на новые пути, удаляет записи треков, которых нет ни в библиотеке, ни в пуле и резерве,
    ни в карантине, и не трогает выданные воркеру.
  - До первого прохода воркеру выдаются только треки пула, чтобы перенос не потерялся.
  - `status()` считает только треки библиотеки Navidrome.
- `navidrome_db.py`: `NdSong.mbid`, `mbids_by_paths` (включая пропавшие файлы).
- Шаблоны: `server/.env.example` (новый: `YANDEX_USERS`, `LISTENBRAINZ_TOKEN`, `LISTENBRAINZ_USERS`) и
  `server/docker-compose.example.yml` с комментариями по формату. Таблица переменных в `server/README.md`.

Приложение (0.20.0):
- `core/downloads`: `EngineSource` — новые счётчики и `active`; `HarvestAccount.navidromeUser`, `reserveStates`;
  `DownloadsClient.linkYandex`.
- `ui/screens/settings/RecoScreen.kt`:
  - строка источника «Предложено · скачано · в очереди · качается · не найдено · в библиотеку · отклонено» и
    выученный вес;
  - при ошибке конфигурации — серое название, текст ошибки, переключатель выключен и неактивен;
  - у аккаунта Яндекса — к кому он привязан, кнопка «Привязать»/«Изменить» (диалог с логином), резерв по той же
    схеме статусов.

Тесты: `server/tests/test_reco_fixes.py`. Покрыто:
- привязка: переменная, приложение, имя файла токена; токены через привязку; адаптер и его ошибки; харвестер с
  привязкой и без, перенос старого резерва; ListenBrainz по пользователю;
- статусы кандидатов и разбивка по источникам;
- зависшая заявка: повтор, затем «не найдено»; плановая пауза источника зависанием не считается;
- хэш звука не зависит от тегов (FLAC, MP3, Ogg);
- перенос анализа по хэшу и MBID пропавшего трека, карантин, удаление, счётчик по библиотеке.

`test_analysis.py` обновлён под новый порядок (сначала обслуживание).

## Что нужно сделать на сервере

1. Обновить образ `bodrod` до тега этого задания (`docs/INFRA.md`).
2. Привязка аккаунтов Яндекса — одно из двух:
   - в `/volume1/docker/bodrod/secrets/env` (его читает entrypoint) добавить
     `export YANDEX_USERS=<логин_navidrome>:jappi,<логин_navidrome_жены>:kalainidi`;
   - или после обновления в приложении: «Настройки → Рекомендации → Архив Яндекса → Привязать» у каждого аккаунта.

   Если пользователи Navidrome и есть `jappi` и `kalainidi`, а файлы токенов называются так же, привязка не нужна.
   Тогда ошибка «пуст» значила бы, что архив записан под другими именами: смотреть `harvest.*` в логе.
3. ListenBrainz: в тот же `env` — `export LISTENBRAINZ_TOKEN=…` (или файл `/secrets/listenbrainz_token`) и
   `export LISTENBRAINZ_USERS=<логин_navidrome>:<логин_lb>,…`.
4. После старта проверить в логе `bodrod`:
   - «Архив Яндекса: аккаунты jappi → …, kalainidi → …»;
   - через несколько минут — «Анализ: обслуживание — {keyed: …, adopted: …, removed: …}». Первый проход
     вычисляет хэши всех старых записей анализа (читает до мегабайта каждого файла, кроме FLAC) и может идти
     несколько минут.
