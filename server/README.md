# bodrod — сервис загрузок BodroMusic

Небольшой сервис рядом с Navidrome. Через него приложение ищет музыку, которой нет в библиотеке, и скачивает её
по **цепочке источников** (с 0.7.0, раздел «Цепочка источников»): Яндекс Музыка → slskd (Soulseek) →
YouTube Music → Lidarr. Для трека, альбома, исполнителя и «меток» Lidarr источники пробуются сверху вниз до первого
успешного;

- **трек в Soulseek**: сервис ищет файл, выбирает лучший вариант и при неудаче переключается на следующего пира;
- **исполнитель целиком через Lidarr** (последний вариант): сервис добавляет артиста с мониторингом всей
  дискографии и запускает поиск альбомов;
- если заданы `SLSKD_DOWNLOADS_DIR` и `LIBRARY_DIR`, сервис сам находит скачанный файл, кладёт его в библиотеку
  под понятным именем (`Исполнитель/Альбом/Исполнитель - Название.mp3`), прописывает теги и обложку из каталога
  и удаляет исходник из папки slskd;
- затем сервис запускает сканирование Navidrome и ждёт, пока трек появится в библиотеке. Приложение
  опрашивает сервис и показывает уведомление «Трек скачан». Нажатие на уведомление сразу включает трек.

Каталоги для «понимания» запроса: **Яндекс Музыка** (основной) и **Deezer** (запасной, если Яндекс не ответил
или ничего не нашёл). Если запрос похож на название песни («город сочи»), приложение предлагает конкретные треки
(«Трофим — Город Сочи»). Если запрос похож на имя исполнителя («трофим»), приложение показывает его популярные
треки и кнопку «Скачать всё».

## Требования

- Navidrome, slskd и Lidarr уже работают;
- корневая папка Lidarr находится внутри библиотеки Navidrome. Папка загрузок slskd может лежать где угодно
  (даже под `.ndignore`), если смонтировать её в bodrod и задать `SLSKD_DOWNLOADS_DIR` и `LIBRARY_DIR`. Без этих
  переменных папка загрузок slskd должна быть внутри библиотеки, а теги остаются такими, какие пришли из Soulseek;
- есть учётка администратора Navidrome. Она нужна для `startScan` и для проверки, есть ли трек в библиотеке.

## Запуск

```bash
cp docker-compose.example.yml docker-compose.yml   # подставьте адреса
mkdir -p secrets && printf '%s' 'пароль-админа-navidrome' > secrets/navidrome_password && chmod 600 secrets/*
cat > .env <<'EOF'
SLSKD_API_KEY=...
LIDARR_API_KEY=...
EOF
docker compose up -d
curl http://localhost:8790/api/health
```

Образ собирается в CI и публикуется как `ghcr.io/jappiy/bodromusic-server` (amd64 и arm64).
Если пакет приватный, выполните `docker login ghcr.io` или сделайте пакет публичным в настройках GitHub.

В приложении: **Настройки → Загрузки** → адрес сервиса (например, `192.168.1.10:8790`) → «Сохранить и проверить».
HTTP разрешён только для адресов локальной сети. Снаружи открывайте сервис через HTTPS (reverse proxy).

## Цепочка источников (0.7.0)

| Источник | Трек | Альбом | Исполнитель | Качество |
|---|---|---|---|---|
| Яндекс Музыка (`yandex`) | да | да, целиком по ID | да, все альбомы | FLAC, иначе AAC (MP4) |
| Soulseek (`slskd`) | да | нет (альбомы — через Lidarr и Soularr) | нет | как у пира |
| YouTube Music (`youtube`) | да | да | да | opus / m4a без перекодирования, всегда lossy |
| Lidarr (`lidarr`) | нет | да, мониторинг одного альбома | да, вся дискография | профиль Lidarr |

- Порядок и переключатели хранятся в БД bodrod и меняются в приложении («Настройки → Источники загрузки», только
  администраторы). **Выключен** — решение администратора; **недоступен** — источник не может работать (нет
  подписки Плюс, не задан токен или `LIBRARY_DIR`, yt-dlp не запускается). И то, и другое цепочка пропускает,
  с записью в лог и в историю попыток заявки (`attempts` в API, в приложении — под заявкой).
- Итоговый источник (`source`: «Яндекс Музыка, FLAC», «Soulseek, MP3», «YouTube Music, Opus») показывается в заявке.
- Не нашли ни в одном источнике — повтор цепочки через `SLSKD_RETRY_INTERVAL_S`, до `SLSKD_RETRY_ROUNDS` раз.
- **Сопоставление** (Яндекс и YouTube): поиск «артист + название», нормализация (регистр, ё/е, скобки, feat,
  транслит), длительность ±3 с; варианты remix / live / cover / karaoke / клип отбрасываются, если их нет в запросе.
  Нет уверенного совпадения — источник неудачный. YouTube берёт только результаты типа «song» (официальное аудио).
- **Защита от превью:** файл короче 90 % длительности по каталогу удаляется, источник неудачный.
- **Яндекс:** библиотека yandex-music (MarshalX) с `[crypto]` — lossless приходит в `encraw` и расшифровывается.
  Пауза 2–3 с между запросами общая для заявок и выгрузки. Подписка проверяется при старте и раз в сутки;
  без неё «Яндекс: скачивание» недоступен. Теги (исполнитель, альбом, номер, диск, год, жанр, текст) и обложка
  1000×1000 — из Яндекса.
- **«Яндекс: метаданные»** — отдельный переключатель: поиск, теги, обложки и тексты из Яндекса для глобального
  поиска, обслуживания и файлов из slskd и YouTube (перетегирование при уверенном совпадении). Работает и на
  бесплатном аккаунте. Выключен — Яндекс пропускается в цепочках каталогов.
- **YouTube:** ytmusicapi + yt-dlp отдельным процессом; yt-dlp обновляется в `<DATA_DIR>/ytdlp` (кнопка в
  приложении, при старте и раз в сутки), новая версия действует сразу. Прокси — `YOUTUBE_PROXY`.
- Прямые источники кладут каждый файл в библиотеку сразу (`LIBRARY_LAYOUT`, для альбома папка — исполнитель
  альбома). Каждый положенный bodrod файл записан в таблицу `library_files` (источник, кодек, `lossy`, id в
  источнике) — после перезапуска уже положенное не качается снова.
- **Исполнитель:** если дискографию скачал Яндекс или YouTube, исполнитель добавляется в Lidarr только для новых
  релизов (`monitor: future`). **«Метки» Lidarr:** раз в час bodrod берёт недостающие альбомы отслеживаемых
  исполнителей (`/wanted/missing`) и пробует их Яндексом и YouTube (служебный пользователь `lidarr`, в приложении
  не видно). Скачанное → Lidarr пересканирует исполнителя (`RefreshArtist`) и снимает метку; не найденное остаётся
  Lidarr и Soularr, как раньше.
- **Массовая выгрузка из Яндекса:** «Мне нравится», мои плейлисты и полные дискографии отмеченных артистов (список —
  из лайков). Отдельная очередь: по одному треку, пауза `EXPORT_DELAY_S`, уступает заявкам, ждёт, пока Яндекс
  недоступен; переживает перезапуск; пропускает имеющееся. Плейлисты в конце пишутся в
  `<LIBRARY_DIR>/Плейлисты Яндекса/*.m3u8` (Navidrome импортирует их сам).

## Архив Яндекса для рекомендаций (0.8.0)

Пока жива подписка Плюс, bodrod собирает с аккаунтов пользователей всё, что потом нужно движку рекомендаций
(`bodrod/reco/harvest.py`). Каждый аккаунт привязан к своему пользователю Navidrome, данные раздельные. Проход —
раз в 10 минут; сборщик работает, когда ему пора:

| Сборщик | Как часто | Что пишет |
|---|---|---|
| Лайки и дизлайки | раз в сутки | лайки треков, альбомов, артистов; дизлайки — в чёрный список пользователя |
| Похожие треки | пока есть необработанные лайки | рёбра `similar` (разовый проход, продолжается после обрыва) |
| Похожие артисты | топ-200, раз в 30 дней | рёбра `artist_similar` |
| Моя волна | 3 раза в сутки | рёбра `wave`: 24 режима по кругу (характер × настроение × язык), 5 пачек подряд, `queue` — последний трек пачки; настройки волны аккаунта сохраняются и восстанавливаются, фидбек не отправляется |
| Персональные плейлисты | раз в сутки | рёбра `playlist` (снимок дня) |
| История | раз в сутки | рёбра `history`, если API отдаёт |
| Чарт и новинки | раз в сутки, с первого аккаунта | общие рёбра `chart` и `new_release` |
| Предзакачка | каждый проход, пока есть Плюс | лучшие по частоте в волне и похожих — в `RESERVE_DIR`, до 500 на пользователя |

Сырые ответы — в `YANDEX_ARCHIVE_DIR`, нормализованное — в таблицы `y_tracks`, `y_artists`, `y_albums`, `y_likes`,
`reco_edges` (семя → кандидат: тип, ранг, сколько раз встречалось). Ошибка доступа (нет Плюса, токен отозван)
отключает только свой сборщик, через 7 дней — новая попытка. Состояние — `GET /api/v1/reco/harvest`.

## Discovery-пул «На пробу» (0.9.0)

Новые треки сначала попадают в `DISCOVERY_DIR` (Navidrome их видит), а в библиотеку их переводят сигналы
пользователя (`bodrod/reco/pool.py`). Трек хранится одной копией, владельцы — в `pool_owners` со статусом
`candidate → queued → downloading → in_pool → promoted | rejected | expired | failed`.

- Сигналы: события приложения (`POST /api/v1/feedback`) и лайк/дизлайк в БД Navidrome (из любого клиента).
- Promote: лайк (любого пользователя), 2 полных прослушивания или добавление в плейлист — файл переносится в
  `LIBRARY_DIR` по `LIBRARY_LAYOUT`. Старый id записывается в `replacements`: если Navidrome выдаст файлу новый id,
  приложение перенесёт лайк (`/api/v1/library/check`). Счётчик прослушиваний при смене id не переносится — Subsonic API
  не даёт менять его за другого пользователя.
- Reject: дизлайк — сразу, ранний скип — на второй раз; трек — в чёрный список пользователя на 180 дней.
- Expire: 21 день без прослушиваний или 3 показа в волне без запуска.
- Файл удаляется, только когда трек не держит ни один владелец (другой пользователь или чарт).
- Пополнение раз в сутки (при `< POOL_REFILL_BELOW`): сначала из резерва (`RESERVE_DIR`), затем — движок кандидатов.
- Регламент обслуживания папки пула и резерва не трогает.

## Движок кандидатов (0.10.0)

Раз в сутки (при пополнении пула) `bodrod/reco/engine.py` собирает кандидатов по семенам пользователя:
лайки и топ прослушиваний из БД Navidrome, свежие promote пула; вес семени затухает с полураспадом 90 дней.

| Источник | Что берётся |
|---|---|
| Last.fm | `track.getSimilar`; `artist.getSimilar` → `artist.getTopTracks` (артисты не из библиотеки); теги → `tag.getTopTracks` |
| Deezer | поиск артиста семени → `/artist/{id}/radio` и топ `/artist/{id}/related` |
| ListenBrainz | LB Radio по артистам семян (`LISTENBRAINZ_TOKEN`); Weekly Exploration / Weekly Jams (`LISTENBRAINZ_USERS`) |
| Архив Яндекса | рёбра `similar`, `wave`, `artist_similar` пользователя |

Кандидат проходит, если его нет в библиотеке, пуле, резерве и чёрных списках и это не лайв/караоке/минус/кавер
(если семя не такое). Счёт: Σ (вес источника × схожесть × вес семени), ×1.3 за каждый следующий источник; артисты с
≥ 3 reject — ×0.3; не больше двух треков одного артиста; доля новых артистов — `newArtistShare`. Вес источника =
ручной (приложение) × выученный по доле promote со сглаживанием Beta(2, 2). Отобранное ставится заявками
`pool:<пользователь>` в обычную цепочку источников (Яндекс → slskd → YouTube) и кладётся в `DISCOVERY_DIR`;
сначала пул пополняется из резерва. Скробблинг в ListenBrainz для пользователей включается в Navidrome
(`ND_LISTENBRAINZ_ENABLED=true`, затем токен LB в профиле каждого пользователя).

## Размещение в библиотеке

Шаг `placing` идёт между `downloading` и `importing`. В приложении он виден как «Добавляем в библиотеку».

1. Сервис находит скачанный файл: сначала по пути `<SLSKD_DOWNLOADS_DIR>/<папка у пира>/<имя файла>`, затем
   ищет по имени во всей папке загрузок, сверяя размер. Если за 60 секунд файл не нашёлся, заявка завершается ошибкой.
2. Путь собирается по `LIBRARY_LAYOUT`. Из имени удаляются `/ \ : * ? " < > |` и управляющие символы, каждая часть
   ограничена 120 байтами, кириллица остаётся как есть. Если такой файл уже есть с тем же размером или с нашими
   тегами, повторно файл не кладётся; иначе к имени добавляется ` (2)`, ` (3)`.
3. Файл копируется во временный `.<имя>.part`, в него записываются теги, затем он атомарно переименовывается,
   так что Navidrome никогда не видит недописанный файл. Пишутся теги artist, albumartist, title, album, а также
   обложка, если её нет в файле (до 8 МБ). Номер трека, диск, год, жанр и текст пишутся, только если их дал
   каталог (Яндекс), иначе не трогаются. Поддерживаются MP3 (ID3v2.4),
   FLAC, M4A/AAC/ALAC, OGG Vorbis и Opus.
4. Исходник удаляется (`DELETE_SOURCE=true`), вместе с папкой пира, если она опустела.
5. Запускается сканирование Navidrome.

Шаг переживает перезапуск контейнера: путь назначения запоминается до копирования, поэтому дубль не появится.
Права на файлы и папки задаются umask процесса. Запускайте контейнер под владельцем музыки (`user: "UID:GID"`).

## Как выбирается файл в Soulseek

Поиски идут очередью: не больше `SLSKD_PARALLEL_SEARCHES` одновременно и с паузой `SLSKD_SEARCH_GAP_S`.
Каждая заявка пробует до трёх запросов: «исполнитель название» → только основной исполнитель (без feat.,
второстепенных и списков через запятую) → транслит (для кириллицы) или одно название. Не нашли ни по одному —
заявка ждёт `SLSKD_RETRY_INTERVAL_S` и пробует снова, до `SLSKD_RETRY_ROUNDS` раз. В сообщении заявки видно,
какие запросы пробовали и сколько было ответов и файлов до фильтрации — то есть отсеял ли их фильтр качества.

Подходят только аудиофайлы, в имени которых есть все слова названия песни, а в пути есть имя исполнителя
(сравнение в латинице: файл `Kirkorov - Luiza.mp3` подходит к заявке «Киркоров — Луиза»).
Отбрасываются ремиксы, live, караоке, минусовки и т. п., если их не было в запросе. Также отбрасываются файлы,
длительность которых отличается от каталожной больше чем на 20 с, и lossy-файлы с битрейтом ниже `MIN_BITRATE`.
Из оставшихся файлов выше ставятся lossless, файлы с совпадающей длительностью и пиры со свободным слотом,
короткой очередью и высокой скоростью. От каждого пира берётся один лучший файл. Если пир не отдаёт файл, сервис
переходит к следующему.

## Раздел «На удаление» и чёрный список

Доступно только администраторам Navidrome. Нужна папка данных Navidrome в контейнере bodrod. Монтируйте её
**без `:ro`**: Navidrome пишет БД в режиме WAL, и SQLite для чтения нужен доступ к файлу `-shm`. Сам bodrod
открывает БД только на чтение (`mode=ro`).

```yaml
volumes:
  - /volume1/docker/bodromusic/navidrome:/navidrome
environment:
  NAVIDROME_DB: /navidrome/navidrome.db
  LIDARR_MUSIC_DIR: /volume2/music
```

Дизлайк — оценка 1 в Navidrome. «Не нравятся всем» — дизлайк поставили все люди (служебные учётки не считаются).

Что происходит при удалении трека:
1. «Исполнитель + название» (без регистра, скобок и feat) попадают в чёрный список.
2. Файл из библиотеки Lidarr удаляется через Lidarr. Если в альбоме не осталось файлов, мониторинг альбома
   снимается, чтобы Lidarr и Soularr не скачали его снова. Остальные файлы просто удаляются с диска.
   Папка альбома, в которой не осталось аудио, удаляется целиком; пустая папка исполнителя — тоже.
   **Если в Lidarr включена корзина (Settings → Media Management → Recycling Bin), файлы Lidarr попадут туда.**
3. Строка трека убирается из очереди slsk-worker (`SLSK_WORKER_QUEUE`).
4. Запускается сканирование Navidrome.

Защита от повторной загрузки: заявки на заблокированные треки bodrod отклоняет. Раз в `BLOCKLIST_SWEEP_S`
bodrod сверяет библиотеку Navidrome с чёрным списком и удаляет вернувшиеся файлы тем же способом, откуда бы они
ни пришли: Lidarr, Soularr, beets, slsk-sweeper, Explo. Трек может прожить в библиотеке до следующего скана
Navidrome (раз в час) плюс 15 минут.

Нагрузка: чёрный список — таблица в SQLite bodrod с уникальным индексом по ключу. 10 000 записей — около 1–2 МБ.
Зачистка читает из БД Navidrome четыре поля по всем трекам и сверяет их с набором ключей в памяти: для
библиотеки в 50 000 треков это доли секунды раз в 15 минут. Если чёрный список пуст, БД Navidrome не читается.

## Обслуживание библиотеки (0.5.0)

Регламент раз в сутки (`MAINTENANCE_AT`) проходит по всем трекам из БД Navidrome. Нужны `NAVIDROME_DB` и доступ
на запись к папке музыки (`MUSIC_DIR`). Отчёт — в приложении: **Настройки → Обслуживание библиотеки** (только
администраторы), там же «Запустить сейчас» и «Вернуть» из карантина. Код — `bodrod/maintenance.py`,
источники обложек и тегов — `bodrod/metadata/lookup.py`.

По порядку:
1. **Короткие и обрезанные файлы.** В карантин — только явные обрезки: lossy-файл весит меньше половины того, что
   должно быть при его битрейте и длительности; FLAC со средним битрейтом меньше 160 кбит/с; короче 60% длительности
   из каталога (для скачанных через bodrod) или полной копии того же трека — если нет признаков другой версии.
   Не трогаются, а пишутся в «требует внимания»: треки короче `MAINTENANCE_MIN_TRACK_S` (короткие треки бывают
   настоящими); треки с `edit`, `radio`, `single`, `version`, `interview`, `live`, `remix`, `intro`, `skit` и т. п.
   в названии, альбоме или имени файла; копии ≥ 50% длины полной и ≥ 2:30 (похоже на радио-версию).
   Счётчики: `short_found` — всего найдено, из них `short_removed` и `short_skipped`.
2. **Дубли треков** — один исполнитель, одно название (без пометок издания: Remastered, Deluxe, год, feat),
   длительность ±3 с. «Live», «Remix», «(Interview)» — отдельные треки. У файлов без тегов исполнитель берётся
   из папки исполнителя, название — из имени файла без номера и «Исполнитель - ». Остаётся копия по порядку:
   качество (lossless, среди lossy — битрейт) → тип релиза (студийный альбом → EP/сингл → сборник/концерт) →
   полный альбом, а не россыпь `Треки/` → папка Lidarr → чистое имя без `.1`, `(1)`, ` copy`. Убираются копии
   из россыпи и копии внутри того же альбома; трек другого полного альбома (сборника) остаётся.
3. **Дубли альбомов** — тот же альбом в нескольких папках: треки переносятся в папку, где их больше; при равенстве —
   в `Исполнитель/ГГГГ - Альбом`; из альбомной папки в россыпь (`Треки/…`) — никогда. Обложка — туда же, пустая
   папка удаляется. Не собираются: многодисковые альбомы, Various Artists, сборники (типовые названия, треки
   разных исполнителей — Sting и The Police). Перенос из папки варианта исполнителя (`Заточка feat. X`,
   `Anacondaz & Кис-кис`) — отдельное действие «Объединение исполнителя» (`artist_merge`).
4. **Чужой релиз** (`mismatch`) — исполнитель в тегах (или в префиксе имени файла) большинства треков папки
   не совпадает с папкой исполнителя (с учётом регистра, `ё/е`, `&`/`feat.` и транслита). Только отчёт.
5. **Теги и обложки.** Треки, у которых Navidrome показывает «[Unknown Artist]», «[Unknown Album]» или название
   из имени файла, проверяются по тегам файла. Недостающие теги дописываются по цепочке `TAG_PROVIDERS`, только
   при оценке совпадения ≥ 0,85 (исполнитель и название с транслитом) и длительности ±3 с; заполненные теги не
   трогаются. Папке альбома без обложки добавляется `cover.jpg` по цепочке `COVER_PROVIDERS`; в папках россыпи
   (`Треки/<исполнитель>` и любые папки с треками разных альбомов) обложка вшивается в каждый файл по альбому
   этого трека. Сначала берётся обложка соседнего трека того же альбома. Не скачалась у источника — следующий.
   В действии написано, из какого источника данные.

Источники: `yandex`, `deezer` (каталог глобального поиска), `itunes` (iTunes Search API, обложки 1200×1200),
`musicbrainz` (MusicBrainz + Cover Art Archive, не чаще 1 запроса в секунду, User-Agent с контактом),
`discogs` (только обложки, нужен токен), `lastfm` (`track.getInfo` с автоисправлением опечаток, обложка альбома;
нужен `LASTFM_API_KEY`). Лимит запросов за запуск — `MAINTENANCE_CATALOG_LIMIT`.

**Last.fm — дополнительный канал** (с 0.6.0): по умолчанию стоит последним в каждой цепочке и срабатывает, когда
остальные ничего не нашли или не ответили. Если Last.fm недоступен (3 сбоя подряд: тайм-аут, HTTP 5xx, ошибка
лимита), bodrod 5 минут его не опрашивает — запросы сразу идут к остальным источникам, бюджет регламента не
тратится. «Не найдено» (ошибка 6) сбоем не считается.

**Пробный режим** (`MAINTENANCE_DRY_RUN=true`) ничего не меняет и ничего не запоминает: два пробных запуска подряд
дают одинаковые счётчики. Запланированные исправления помечены `planned` и сформулированы как «будет убрано /
будет добавлено». В настоящем режиме то, что не удалось исправить, попадает в отчёт один раз (повтор — через 30 дней
или после изменения файла); отметки «не найдено» для тегов и обложек хранят версию списка источников и
сбрасываются при его смене. При обновлении с 0.4.0 кэш проверок очищается (его записали пробные запуски).

**Статистика запуска** — всегда все ключи: `songs`, `short_found`, `short_removed`, `short_skipped`,
`duplicates_removed`, `albums_merged`, `artists_merged`, `tags_fixed`, `tags_problems`, `covers_added`,
`covers_missing`, `mismatches`, `quarantine_purged`, `attention` (= `short_skipped` + `tags_problems` +
`covers_missing` + `mismatches`).

После изменений запускается сканирование Navidrome.

**Lidarr.** Если задан `LIDARR_MUSIC_DIR`, файлы из папок исполнителей Lidarr не переносятся и не убираются
(иначе Lidarr скачал бы их снова) — только в отчёт. Если Lidarr недоступен, запуск откладывается.

**Карантин.** Убранное перемещается в `QUARANTINE_DIR/<номер запуска>/<путь>` (в папке лежит `.ndignore`,
Navidrome её не сканирует) и удаляется через `QUARANTINE_DAYS` дней.

**Лайки.** Лайк в Navidrome привязан к id трека. bodrod запоминает, какой файл занял место убранного или
перенесённого (таблица `replacements`), а приложение через `POST /api/v1/library/check` переносит лайк
пользователя на оставшуюся копию и убирает из «Любимого» удалённые треки.

## API

Авторизация — заголовки `X-Subsonic-User`, `X-Subsonic-Token`, `X-Subsonic-Salt` (как в Subsonic API:
`token = md5(password + salt)`). Сервис проверяет их запросом `ping` к Navidrome. Каждый пользователь видит только
свои заявки.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/health` | Проверка живости, без авторизации |
| GET | `/api/v1/info` | Версия и возможности (`trackDownloads`, `albumDownloads`, `artistDownloads` — есть включённый и доступный источник; `sources` — экран источников) |
| GET | `/api/v1/discover?q=` | Глобальный поиск: `intent` (`track` / `artist` / `none`), треки, исполнители, популярные треки |
| GET | `/api/v1/artists/top?source=&id=` | Популярные треки исполнителя |
| GET | `/api/v1/artists/popular?name=` | Популярные треки исполнителя по имени (Яндекс Музыка), с `librarySongId` у тех, что есть в библиотеке |
| POST | `/api/v1/library/check` | `{ids: [...]}` → `{missing: [...], replaced: {старый id: новый}}` — удалённые и заменённые треки |
| GET | `/api/v1/requests` | Заявки пользователя |
| POST | `/api/v1/requests` | `{kind: "track", artist, title, durationMs?}`, `{kind: "album", artist, album}` или `{kind: "artist", artist}`. В ответе — `source` и `attempts` |
| GET | `/api/v1/requests/{id}` | Одна заявка |

| POST | `/api/v1/sources/youtube/update` | Обновить yt-dlp сейчас (502 — не удалось) |

| POST | `/api/v1/yandex/export/pause` | Пауза |
| GET / PUT | `/api/v1/yandex/export/artists` | Артисты из лайков; PUT `{selected: [id...]}` — кого брать целиком |
| POST | `/api/v1/yandex/export/artists/refresh` | Собрать артистов из «Мне нравится» заново |
| POST | `/api/v1/feedback` | `{events: [{songId, event, positionMs?, durationMs?, context?, at?}]}` — события: `started`, `skipped`, `completed`, `liked`, `unliked`, `disliked`, `playlisted`, `shown`; в ответе — сменившиеся статусы треков пула |
| GET | `/api/v1/pool` | Пул пользователя: треки `in_pool`, счётчики по статусам, размер |
| POST | `/api/v1/pool/status` | `{ids: [...]}` → `{id: статус}` только для треков пула |
| GET | `/api/v1/pool/hidden` | Что приложение прячет: `songIds` пула, `albumIds` и `artistIds`, у которых все треки в пуле |
| POST | `/api/v1/pool/refill` | Пополнить пул сейчас (202) |
| GET / PUT | `/api/v1/reco/engine` | Источники движка: `enabled`, `weight`, `learnedWeight`, счётчики; PUT `{enabled?, weights?, newArtistShare?}` (только админ) |
| GET | `/api/v1/reco/engine/preview?limit=` | Что движок предложил бы пользователю сейчас (без загрузки) |
| GET | `/api/v1/reco/harvest` | Архив Яндекса: по аккаунтам — сборщики (когда работали, отключены ли), лайки, рёбра, резерв (только админ) |
| POST | `/api/v1/reco/harvest/run` | Пройти по аккаунтам сейчас |

Статусы заявки: `queued → searching → downloading → importing → completed`, либо `failed` / `cancelled`.
Прямые источники (Яндекс, YouTube) сразу идут в `downloading`. Заявка, не найденная ни в одном источнике,
возвращается в `queued` до следующего прохода цепочки. Исполнитель, удалённый из Lidarr,
сразу завершается с `failed` («Артист удалён из Lidarr»).
